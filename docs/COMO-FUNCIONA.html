Como o nosso projeto funciona

Explicado do zero — sem assumir nenhum conhecimento prévio. Projeto CSI-10 (ITA).

1. O que é, em uma frase

É um site de mapa que mostra, de forma visual e estatística, onde e quando aconteceram as ocorrências criminais no Estado de São Paulo (2022–2026), usando os dados abertos oficiais da SSP-SP (Secretaria de Segurança Pública). São 5,17 milhões de registros.

2. A grande imagem: as 4 peças

Pense num restaurante. Quatro peças trabalham juntas:

As 4 peças. As 3 primeiras ficam no ar o tempo todo; o ETL roda só de vez em quando, para preparar os dados.

  • Frontend (o salão): é a única parte que você vê. É o mapa, os filtros, a barra do tempo. Abre no seu navegador.
  • API (o garçom): fica entre o mapa e o banco. O mapa nunca fala direto com o banco; ele faz um pedido ("me dê os furtos de 2024 em SJC") e o garçom traz a resposta.
  • Banco de dados (a despensa): guarda os milhões de registros já organizados e responde perguntas geográficas muito rápido.
  • ETL (o preparo, antes do restaurante abrir): pega as planilhas cruas da SSP-SP, limpa, organiza e enche a despensa. Roda uma vez (ou quando trocamos os dados) — não fica no ar.

3. Onde tudo mora (a hospedagem)

Tudo roda numa única máquina virtual (uma "VM") no Google Cloud. Uma VM é um computador que não existe fisicamente na sua mesa: é alugado na nuvem e fica ligado 24 horas, com um endereço na internet. Dentro dessa VM, cada peça roda dentro de um container Docker — uma "caixinha" isolada que já vem com tudo que aquela peça precisa para funcionar igual em qualquer lugar.

4 containers Docker dentro da mesma VM. Só o Caddy é exposto à internet; o banco fica protegido na rede interna.

📌 Por que numa VM única? Os planos gratuitos de banco na nuvem (≈0,5 GB) não caberiam os 5,17 milhões de linhas. Uma VM (no crédito de testes de 90 dias do Google Cloud) cabe tudo, de graça e num só lugar.

4. O banco de dados

Usamos o PostgreSQL (um dos bancos de dados mais usados do mundo) com a extensão PostGIS, que dá a ele "superpoderes geográficos": ele sabe calcular coisas como "quais ocorrências estão dentro de São José dos Campos + 15 km" usando matemática de mapas, em milissegundos.

  • Onde está: dentro do container db, na VM do Google Cloud.
  • O que guarda: a tabela ocorrencias (5.168.102 linhas: cidade, bairro, tipo de crime, mês/ano e a posição no mapa) e a tabela municipios (os 645 contornos das cidades de SP, baixados do IBGE — usados no filtro e no buffer).

5. O ETL — preparar os dados (pasta etl/)

ETL = Extract, Transform, Load (Extrair, Transformar, Carregar). É a "cozinha" que transforma as planilhas bagunçadas da SSP-SP em dados limpos no banco. São scripts escritos em TypeScript (uma versão do JavaScript com tipos, rodando no Node.js). Cada um faz uma coisa:

ScriptO que faz
index.tsLê as 9 planilhas semestrais (Jan/2022–Abr/2026), conserta a codificação (acentos), unifica colunas que mudam de nome a cada ano, trata coordenadas inválidas e gera um arquivo limpo (ocorrencias_limpas.csv).
load.tsCarrega esse arquivo limpo no banco (comando COPY, o jeito mais rápido de inserir milhões de linhas) e cria os índices.
municipios.tsBaixa do IBGE os 645 contornos das cidades de SP e grava na tabela municipios.
centroides_bairro.tsPara as ocorrências sem coordenada exata, busca o centro do bairro no OpenStreetMap (e no Nominatim) e preenche a posição — sem nunca jogar tudo no centro da cidade (evita "falso ponto quente").

Resultado: 88% das ocorrências ficam plotáveis no mapa; o que não casa fica oculto (mas continua contado nos números).

6. A API — o "garçom" (pasta api/)

É um programa em Node.js usando o framework Fastify. Ele fica "de plantão" esperando pedidos do mapa e, para cada pedido, monta uma consulta ao banco e devolve só os dados certos. As principais "portas" (rotas) são:

RotaPara que serve
/api/heatmapDevolve a densidade (mapa de calor) da área visível.
/api/pontosDevolve os pontos individuais (quando se dá zoom).
/api/statsOs números do painel (total, exatos, etc.).
/api/buffer e /api/extentA área de vizinhança (cidade + raio) e o enquadramento do mapa.
/api/naturezas, /api/municipios, /api/periodoListas para os filtros e a barra do tempo.

7. O frontend — o mapa que você vê (pasta web/)

É o site em si, escrito em React (uma biblioteca para montar telas) com TypeScript, e usa o OpenLayers — uma biblioteca especializada em desenhar mapas. As partes:

ArquivoO que faz
MapView.tsxO mapa em si: mapa de calor, pontos coloridos por tipo de crime, popups e o buffer.
Sidebar.tsxA barra lateral: filtros de cidade e de natureza, números e legenda.
TimeSlider.tsxA barra do tempo embaixo (play, início e fim do período).
App.tsxO "maestro": guarda o estado e liga tudo.
🗺️ Detalhe sobre o OpenStreetMap: ele aparece em dois papéis. As imagens do mapa base (as ruas) são "ladrilhos" do OpenStreetMap. E os dados do OpenStreetMap (a base de bairros nomeados) foram usados no ETL para achar os centros dos bairros. Mesma fonte, usos diferentes.

8. Do GitHub ao site (deploy automático)

O GitHub é onde o código fica guardado na nuvem (e onde a dupla colabora). Configuramos um deploy automático (CI/CD): toda vez que alguém envia uma mudança (git push), uma "esteira" (GitHub Actions) atualiza o site sozinha, em ~1–2 minutos.

A Action conecta na VM (via SSH), envia o código novo e reconstrói os containers — sem ninguém mexer na VM.

O endereço do site: https://34-39-181-38.nip.io (seguro, com cadeado) — e também http://34.39.181.38.

10. Glossário (para consultar)

Para quem nunca programou: os blocos básicos

Código / programa
Uma sequência de instruções escritas que diz ao computador exatamente o que fazer. Um "programa" é um conjunto dessas instruções com um objetivo.
Linguagem de programação
O "idioma" em que o código é escrito. Cada uma tem suas regras. Aqui usamos principalmente o JavaScript.
JavaScript
A linguagem mais usada da web. Originalmente rodava só dentro do navegador (para deixar os sites interativos).
TypeScript
Uma versão do JavaScript que adiciona "tipos" — uma checagem que avisa erros antes de rodar (ex.: garante que uma latitude seja sempre um número). Mais seguro para projetos grandes.
Navegador (browser)
O programa que você usa para abrir sites (Chrome, Firefox, Edge…). É onde o nosso mapa aparece.
Servidor
Um computador ligado o tempo todo que serve (entrega) páginas e dados para quem acessa pela internet.
Biblioteca / framework
Código pronto, feito por outras pessoas, que a gente reaproveita para não reinventar a roda. React, Fastify e OpenLayers são exemplos.

As tecnologias do nosso projeto

Node.js
Um programa que permite rodar JavaScript fora do navegador — num servidor. É o "motor" que faz a nossa API e os scripts de dados funcionarem.
Fastify
Uma biblioteca (framework) para Node.js que facilita construir uma API — o programa que recebe pedidos e responde. Escolhido por ser rápido. É a nossa camada de "garçom".
React
Uma biblioteca para construir interfaces (telas) interativas no navegador. É com ela que montamos os botões, filtros e painéis do site.
OpenLayers
Uma biblioteca especializada em desenhar mapas interativos (zoom, camadas, pontos, mapa de calor). É o "motor cartográfico" do frontend.
Vite
Uma ferramenta que empacota o código do frontend para o navegador conseguir abrir rápido. Também roda o site na sua máquina enquanto a gente desenvolve.
Banco de dados
Um programa que guarda dados organizados e responde perguntas sobre eles muito rápido — como uma planilha gigante e poderosa.
PostgreSQL
O banco de dados que usamos: um dos mais sólidos e usados do mundo, gratuito e de código aberto.
PostGIS
Uma "extensão" (complemento) que dá ao PostgreSQL superpoderes geográficos: ele passa a entender mapas e calcular coisas como "o que está dentro desta área" em milissegundos.
API
Uma "ponte" por onde um programa pede dados a outro, em formato organizado. Aqui, o mapa (frontend) pede à API, que consulta o banco e devolve só o necessário.
Frontend / Backend
Frontend é a parte visível (o site no navegador). Backend são os bastidores (a API e o banco), que o usuário não vê.
Docker
Uma tecnologia para empacotar um programa com tudo que ele precisa dentro de uma "caixinha" padronizada, para que rode igual em qualquer computador — acabando com o clássico "na minha máquina funcionava".
Container
A "caixinha" do Docker em execução: uma cópia isolada e leve de um programa rodando. No projeto, cada peça (banco, API, site) roda no seu próprio container.
Nginx
Um servidor web: um programa que recebe os pedidos do navegador e devolve os arquivos do site (e pode repassar pedidos para a API). É quem entrega o nosso frontend.
Caddy
Parecido com o Nginx, mas com um truque: ele obtém e renova sozinho o certificado de HTTPS (o cadeado de segurança). Fica "na frente" de tudo, cuidando da segurança.
HTTPS / certificado
O "cadeado" do navegador. Criptografa a conexão entre o visitante e o site, para ninguém bisbilhotar no caminho.
VM (máquina virtual)
Um computador que não fica na sua mesa: é alugado na nuvem (no nosso caso, no Google Cloud), fica ligado 24h e tem um endereço na internet. É onde tudo roda.
Git / GitHub
Git é um sistema que guarda o histórico de todas as versões do código (como "fotos" do projeto). GitHub é o site que hospeda esse histórico na nuvem e deixa a dupla trabalhar junto.
CI/CD (deploy automático)
Uma "esteira" que, ao receber código novo no GitHub, atualiza o site sozinha, sem ninguém mexer no servidor.
ETL
Extract, Transform, Load (Extrair, Transformar, Carregar): o processo que pega os dados crus, limpa/organiza e coloca no banco.
Heatmap (mapa de calor)
Mancha colorida que mostra onde há mais ocorrências (vermelho = mais denso, azul = menos).
Buffer
Uma área expandida em torno de uma cidade (ex.: cidade + 15 km), para incluir a vizinhança na análise.
